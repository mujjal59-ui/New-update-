CRITICAL TERMUX REQUIREMENT
The existing direct Termux command-running capability is a protected core feature.
1. Locate and document the exact current implementation: command dispatch, intents/deep links, Termux:Tasker/Termux:API integration if present, scripts, permissions, package names, working directory, environment variables, stdout/stderr, exit-code handling, callbacks, timeout and error handling.
2. Preserve the existing implementation and its current user experience. Do not replace it with a simulated terminal, web terminal, remote server, shell imitation or a new command runner.
3. Do not claim commands ran unless the real Termux process/bridge confirms execution and returns a verifiable result.
4. Do not broaden permissions or execute arbitrary commands silently. Keep explicit user confirmation, command preview, risk warning and audit log where applicable. Never expose secrets in logs.
5. Add regression tests proving existing Termux command execution still works for safe representative commands, including success, failure, output, cancellation/timeout and unavailable-Termux cases. Use the actual integration path and device testing where possible.
6. If source inspection shows Termux support depends on an external companion app, plugin, permission or setup, document it accurately. Do not invent a bridge or promise universal support.
7. If an architecture change is unavoidable, stop and explain the exact incompatibility and migration plan; do not remove the old working path without approval.
